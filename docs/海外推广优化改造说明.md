# 家宴海外推广优化改造说明

> 文档状态：需求梳理草案
>
> 更新日期：2026-11-10
>
> 适用范围：家宴 Web/PWA、现有 Android WebView 外壳，以及未来可能的应用商店版本

## 一、背景与目标

家宴目前围绕家庭菜品管理、点菜、共同点菜、买菜清单、AI 营养分析和吃饭日记设计，界面与内容以中文家庭场景为主。海外推广需要在保留家庭聚餐体验的同时，让目标用户能够理解、信任并顺利完成核心流程。

建议先确定首发国家或地区、主要用户群体与发布渠道。本文以**海外华人及英语用户**为第一阶段假设；英语并不代表所有海外用户的语言和饮食习惯。具体法规、内容、服务商和渠道要求应在目标市场确定后复核。

### 目标用户与场景

1. **海外华人家庭**：用中文管理家常菜，与使用英文的家人或朋友共同点菜。
2. **英语用户**：建立家庭常做菜清单，邀请家人选择，整理采购与记录用餐。
3. **聚餐受邀者**：无需先理解产品全部功能，即可通过链接查看菜单并参与选择。

### 成功标准

- 用户可用所选语言完成注册、建菜、选菜、邀请、采购清单和用餐记录等主要流程。
- 海外用户能理解数据如何使用、如何求助，以及如何管理或删除账号。
- 在目标地区真实网络及主要移动设备上，关键流程可用、错误可恢复。
- 产品决策基于目标用户访谈与试用数据，不预设所有国家采用相同设计。

## 二、当前项目现状

以下结论基于本地代码与 README 的静态检查，并非线上环境或真实设备验收结果。

- 界面文案主要直接写在 HTML 和 JavaScript 模板中；PWA 配置为中文，菜单及采购清单图片也包含中文文案。
- 已有邮箱密码注册和登录、邮件验证、共同点菜、菜品与照片管理、买菜清单、AI 营养分析和日记等功能。账号页面当前展示邮箱、外观设置及退出登录。
- 共同点菜通过链接邀请，创建页面显示邀请有效期为 1 小时；已加入者在邀请过期后仍可继续点菜。
- 买菜清单和营养分析使用同一 Edge Function，按菜名调用第三方 AI；买菜清单提示词目前针对中国家庭常见做法。营养分析按整桌菜及假设份量估算，页面已有估算说明。
- 菜品和日记照片使用私有对象存储及本地缓存；README 说明旧照片和共享点菜快照可能产生需要后续核对的存储文件。

## 三、优先级定义

| 优先级 | 定义 |
| --- | --- |
| P0 | 首批目标市场发布前必须明确或完成；直接影响核心流程、信任或适用的渠道与法律要求。 |
| P1 | 首发后尽快完成，或在面向当地家庭推广前完成；明显影响本地使用体验。 |
| P2 | 根据用户反馈、目标市场和投入产出决定，不作为首版默认承诺。 |

优先级是产品建议，不代表法律结论；最终以目标市场、产品实际数据处理方式和发布渠道为准。

## 四、UI 与语言改造

| 改造点 | 需求说明 | 优先级 |
| --- | --- | --- |
| 语言选择 | 首版支持简体中文、英文；首次依据设备语言设置默认值，并提供手动切换和记忆选择。 | P0 |
| 文案国际化 | 建立统一文案资源，覆盖页面、表单、空状态、错误、通知、无障碍标签及动态数量；支持复数、变量插值和语言回退。 | P0 |
| 非页面内容翻译 | 覆盖注册及密码恢复邮件、邀请页、分享文案、菜单与采购清单图片、安装信息、帮助和隐私页面。用户自己输入的菜名与日记不自动改写。 | P0 |
| 布局适配 | 检查英文长标题、按钮、弹窗、菜品卡片和纸质菜单；避免固定宽度截断，支持合理换行。 | P0 |
| 本地格式 | 日期、时间、数字按所选地区格式化；语言和地区偏好允许分别设置。 | P1 |
| 品牌名称 | 确定英文展示名、简短介绍及一致的视觉表达，正式使用前核查商标和域名。 | P1 |
| 无障碍 | 检查屏幕阅读器、键盘、焦点、对比度、字号缩放、触控目标和错误提示；纸质菜单提供明确可发现的添加和移除方式。 | P1 |
| RTL 语言 | 架构上避免不必要的左右方向假设；只有确定阿拉伯语等市场后，再实施并测试从右到左布局。 | P2 |

## 五、功能改造

### 5.1 菜品和饮食习惯

| 改造点 | 需求说明 | 优先级 |
| --- | --- | --- |
| 示例菜品 | 按目标市场准备少量本地常见菜与中餐示例，允许空白开始；由目标语言使用者审核名称、描述和图片。 | P1 |
| 分类与搜索 | 检查现有分类、菜系和搜索是否适合目标市场；必要时补充按餐次或菜品类型筛选，并支持用户自定义分类。 | P1 |
| 过敏原 | 菜品可由用户标记常见过敏原；未填写显示“未知”，不能视为安全。展示时说明信息由填写者负责确认。过敏原范围按目标市场确定。 | P1 |
| 饮食偏好 | 视需求支持素食、纯素、不含乳制品等标签；清真等涉及具体食材和制作方式的声明必须由用户确认，不依靠 AI 自动保证。 | P1 |
| 份量与单位 | 用户需要管理食谱或采购用量时，支持份数和公制/美制单位；明确换算与舍入规则。 | P2 |

### 5.2 共同点菜与分享

- **P0：邀请页本地化。** 受邀者按自己的语言理解邀请、菜品、参与身份、错误和结束状态；检查中英文用户混合参与的情况。
- **P0：分享范围透明。** 发起前说明受邀者可看到哪些菜品、照片、参与者名称和选择；设计饮食偏好等新增信息的可见范围。
- **P1：分享方式适配。** 在浏览器支持时提供系统分享，同时保留复制链接及失败回退；在目标用户常用消息应用内验证链接打开体验。
- **P1：邀请管理。** 评估 1 小时是否符合提前安排聚餐的习惯，可设计更长有效期和提前关闭邀请。明确“邀请过期”与“已加入者继续参与”的区别，并验证服务端权限。
- **P2：多语言菜品内容。** 先调研是否需要由创建者填写菜品译名；若引入自动翻译，应允许修改并明确原文和译文。

### 5.3 买菜清单与 AI 营养分析

- **P0：按语言和地区输出。** 清单分类、食材名、营养说明和错误提示跟随用户设置；为目标市场菜品准备评估样本，验证结果可理解且可编辑。
- **P0：告知第三方处理。** 生成前清楚说明发送的数据类型、用途和服务提供方；根据适用法规及渠道要求设计授权和撤回方式。非必要信息不应发送。
- **P0：避免安全误导。** 清单提示用户核对实际做法；营养结果保留估算依据、整桌而非每人、非医疗建议等说明。不凭生成结果保证过敏原或宗教饮食合规。
- **P1：适配当地采购。** 优化本地食材名称、可替代食材和采购分类；保持手动添加、编辑、复制和图片导出。
- **P1：服务稳定性。** 在首发地区测试 AI 服务可用性、延迟、限额、超时和失败提示；评估服务商的覆盖、数据处理和替代方案。
- **P2：更准确的份量。** 允许用户输入人数、食材及用量后再计算；仅凭菜名时继续使用明确标注的估算，避免呈现虚假精度。

### 5.4 账号与数据

- **P0：账号恢复。** 补齐或验证忘记密码、重置密码、验证邮件重发、邮件失效和跨设备登录流程，并提供目标语言邮件。
- **P0：隐私说明。** 提供易访问的隐私政策和联系渠道，说明账号、菜品、照片、邀请、AI 请求等数据的用途、接收方、保存及删除方式。
- **P0：账号和数据删除。** 设计可发现的删除入口、身份验证、确认、执行结果和必要的保留说明。核对账号、数据库、照片、本地缓存、共享快照及第三方处理数据的删除或保留策略；不能只清除前端显示。
- **P1：数据导出。** 提供用户可理解、可使用的数据导出方案，明确照片、菜单、日记和共享内容的覆盖范围；结合目标市场适用的数据权利确定实现。
- **P2：第三方登录。** 根据用户反馈与上架计划评估 Google、Apple 等登录；实施前检查相应平台政策、账号关联与删除流程。

### 5.5 图片、日记和安装体验

- **P0：图片导出。** 菜单与买菜清单图片使用当前语言，检查长菜名换行、字形、预览及下载文件名。
- **P0：海外真实设备验证。** 检查 iPhone Safari、Android Chrome 中的访问、安装到主屏幕、重新打开及版本更新；Android 外壳另做专项验证。
- **P1：离线与同步。** 清楚区分可离线查看的内容和需要联网的操作，验证照片缓存、登录失效、网络恢复及同步失败提示。
- **P1：日记体验。** 验证当地日期显示、多语言输入、照片上传、跨设备查看和数据删除。

## 六、隐私、合规与渠道

具体义务取决于运营主体、目标国家、处理的数据、服务商所在地及发布渠道，需在上线前逐项确认；下列内容用于产品排查，不代替法律审查。

1. **建立数据清单**：记录收集目的、数据类型、存储位置、访问主体、第三方接收方、保留周期与删除方式；核查数据库、照片存储、邮件服务、AI 服务和日志。
2. **评估跨境处理与用户权利**：如适用 GDPR 等规则，核对处理依据、告知、跨境传输，以及访问、更正、删除和可携带等请求的处理方式。并非所有处理都以同意为唯一依据。
3. **应用商店要求**：若提交 Apple App Store，检查账号删除、隐私政策和第三方 AI 数据共享等要求；若提交 Google Play，检查数据安全表单及应用内和网页账号删除请求入口。纯 PWA 不自动适用所有商店提交规则，但仍需遵守适用法律。
4. **敏感信息最小化**：饮食偏好或过敏信息可能涉及敏感个人信息，新增前确认是否必要、可见范围和适用保护要求。
5. **安全与权限**：核对照片访问、邀请令牌、过期和撤销、账号删除及用户隔离；避免将个人数据和令牌写入不必要的日志。

## 七、技术实施建议

1. **先建立国际化基础**：统一语言资源、插值、复数与日期格式；将界面固定文案与用户数据分离。逐步迁移现有普通脚本，检查脚本加载顺序及 Service Worker 缓存清单和版本。
2. **保持存储兼容**：新增语言、地区、饮食标签等字段前设计默认值、数据库迁移及旧客户端兼容策略；不要强制翻译用户已有内容。
3. **明确服务边界**：AI 请求显式传递受支持的语言和地区；服务端校验参数，保持用户隔离、限额和超时处理。改动后验证中英文提示词及返回结构。
4. **图片单独适配**：Canvas 绘图与普通 HTML 各自检查字体、测量宽度、换行及溢出；支持目标语言所需字形。
5. **设计数据生命周期**：实现导出、删除和共享内容处理前，先梳理数据库、私有存储、旧照片引用、缓存和服务商的数据链路，再制定可验证的执行与失败重试方案。
6. **建立市场验证环境**：选定实际地区与设备，记录网络、浏览器、版本和测试账号；不要以本地构建通过替代海外网络、邮件或真实设备结果。

## 八、分阶段计划与验收

### 第一阶段：英文可用版本

**范围**：确认首发市场与渠道；中英文、关键页面和邮件、图片导出、隐私说明、账号恢复及删除方案、AI 数据告知、海外连接与安装体验。

**验收**：

- 中英文用户分别完成注册、添加菜品、选菜、生成清单和记录用餐；切换语言后状态和用户输入不丢失。
- 英文受邀者在移动端打开邀请并完成选菜；邀请失效、网络错误和分享范围有明确提示。
- 对长英文菜名、窄屏、系统大字号、菜单和清单图片做同状态视觉检查，无关键内容遮挡或裁切。
- 账号恢复和删除覆盖实际后端数据及必要的错误处理；按所选发布渠道核验政策要求。
- 记录目标地区真实网络、邮件送达、PWA 更新及 AI 可用性的测试结果和未解决问题。

### 第二阶段：当地家庭体验优化

**范围**：本地示例菜品、分类与搜索、过敏原和饮食偏好、采购清单本地化、邀请管理、数据导出。

**验收**：

- 目标用户能自行建立适合家庭的菜单；未填写的过敏原显示未知，分享范围符合设计。
- 使用目标市场菜品样本检查 AI 输出及失败情况，记录错误并持续修正；不将生成内容当作安全保证。
- 至少完成一次跨语言、跨设备共同点菜及采购清单分享的端到端测试。

### 第三阶段：按反馈扩展

**候选范围**：更多语言、RTL、社交登录、份量和单位换算、更多地区服务商、应用商店上架。

**进入条件**：第一、二阶段关键流程稳定，并有访谈、使用数据或明确市场需求支持；具体范围另行排期。

## 九、待确认事项

1. 首发国家或地区是什么？主要服务海外华人、当地家庭，还是两者兼顾？
2. 首发渠道是现有 PWA、Android 外壳，还是计划提交 Apple App Store 和 Google Play？
3. 是否将英语作为唯一新增语言？品牌英文名是否需要独立设计？
4. 过敏原和饮食偏好是否纳入首发范围？由谁填写、谁可见？
5. AI 服务商、数据存储地区、隐私政策和客服由谁负责评估与维护？
6. 哪些数据应支持导出和删除，历史共享快照、照片及备份如何处理？
